0002 — The LLM Judge (Preview)

Stage 4 — where filtered candidates get a verdict. Ultra-short preview so filtering's output clicks.

What Judge receives

Only filter_candidates() survivors — on your fixtures, 3 candidates total (2 shared_env + 1 shared_volume), not the original 8. Each carries enriched evidence.

Candidate{
  service_a="orders", service_b="reports",
  resource="DB_HOST", resource_type="env_var", value="shared-db",
  evidence="both define DB_HOST='shared-db' ... | filter: kept — shared DB_HOST='shared-db' — specific config"
}

What Judge does (narrow, per AGENTS.md:65)

  • Prompt: "Given this ONE candidate + evidence, is shared resource=value real coupling or coincidence? → {is_dependency: bool, confidence: 0-1, reasoning: str}"
  • Does NOT scan codebase — only judges pre-extracted candidate (DECISIONS.md:D-002 Discovery ≠ Judgment).
  • Cached in cache.json (gitignored) with key = hash(candidate + evidence) — not just DB_HOST=shared-db, because same value means different things in different service contexts (AGENTS.md:85, D-014).
  • Run >1× during validation to check consistency — LLMs are non-deterministic.

Why Filtering → Judge boundary matters

Without filtering: LLM sees PORT mismatches + DATA_PATH noise → wasted tokens, hallucinated edges.
With filtering: LLM sees only DB_HOST/DB_NAME/shared-data with provenance → cheap, repeatable, explainable. Next stages (Model, Graph, Report) preserve that provenance.
