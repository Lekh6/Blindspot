0004 — Tier 2 Map: Same Pipeline, New Sources

Tier 2 adds Kubernetes manifests as a second candidate source. Same 7 stages, same downstream — only Stages 1–2 learn new inputs. 8-minute lesson, one win: you can trace a shared ConfigMap from YAML to graph node without inventing a new architecture.

1. Parse K8s ★→2. Discovery K8s ★→3. Filtering→4. Judge 1/group→5. Model→6. Graph→7. Report
Core rule (AGENTS.md:385, DECISIONS.md:D-012): K8s findings enter the existing pipeline. No separate downstream. Tier 1 taught you Compose → candidates; Tier 2 teaches manifests → same candidates shape.

0. Why Tier 2 exists

Compose covers one file per repo. Real clusters describe coupling in many YAML files: two Deployments can share a ConfigMap name and break together on rename — invisible to network tracing, exactly like DB_HOST sharing in Tier 1. Tier 2 catches shared ConfigMap / shared Secret / shared volume via YAML parsing (pyyaml, already in requirements).

1. Stage 1′ — K8s parse + workload normalization

Input: multi-doc YAML (--- separated). Parse every document, split by kind:

# workloads (become "services") — normalize these:
Deployment / StatefulSet / DaemonSet / Job / CronJob / Pod
  → Workload{ name, namespace (=default if absent), containers[],
              env[], envFrom[], volumeMounts[], volumes[] }

# resources (become candidate targets, NOT services):
ConfigMap / Secret / PersistentVolumeClaim

Preserve metadata.namespace + source file per object — Stage 3 needs both for identity and provenance. Same idea as Tier 1 preserving env_file origin and image:.

# minimal example both workloads reference:
apiVersion: apps/v1
kind: Deployment
metadata: { name: api, namespace: default }
spec:
  template:
    spec:
      containers:
      - name: api
        envFrom:
        - configMapRef: { name: game-demo }   # ← the coupling point

2. Stage 2′ — Candidate discovery (broad, deterministic)

Pairwise over workloads, same as discovery.py:40. Three scanners:

① shared ConfigMap:  envFrom.configMapRef.name
                      env.valueFrom.configMapKeyRef.name
                      volumes.configMap.name
                      volumes.projected.sources[].configMap.name
② shared Secret:      envFrom.secretRef.name
                      env.valueFrom.secretKeyRef.name
                      volumes.secret.secretName
                      projected.sources[].secret.name
③ shared volume:      volumes.persistentVolumeClaim.claimName
                      same hostPath.path (exact match only)

Broad = kube-api-access-* still produces a candidate here; filtering drops it next. Never filter inside discovery.

3. Stage 3′ — Filtering + bounded evidence (the interesting part)

Drop: projected kube-api-access-* (service-account token, like PORT in Tier 1) + generic env keys (PORT/DEBUG/LOG_LEVEL unchanged). Keep: app ConfigMaps (game-demo), credential Secrets (db-creds), shared PVCs.

One bounded package per surviving group (same shape as Tier 1, K8s fields added):

EvidencePackage{
  workload_a: api, workload_b: worker,
  resource: game-demo, resource_type: configmap,
  keys_used: [player_initial_lives] (bounded, not all 20 keys),
  binding: envFrom vs volumeMount:/config (how each consumes it),
  namespace: default,
  resolution: FOUND (object exists, attach data keys)
              / MISSING (referenced but no object → unresolved)
  related_config: sibling refs only (e.g. db-creds alongside game-demo)
}

Identity for aggregation/dedup: configmap:default/game-demo — namespace + type included, so cross-namespace same-name ≠ same resource.

4–7. Unchanged downstream (read once, trust)

  • Stage 4 Judge — same grouped prompt (judge.py:96), 0 calls for noise + 1/group, verdict/confidence/reason, cache key now includes namespace + keys_used + resolution.
  • Stage 5 Model — same CouplingGroup; "service" now holds a workload name.
  • Stage 6 Graph — same bipartite rule: api → configmap:default/game-demo ← worker. Never api → worker.
  • Stage 7 Report/CLI — same report + accounting; CLI input discovery extends to *.yaml alongside docker-compose.yml.
