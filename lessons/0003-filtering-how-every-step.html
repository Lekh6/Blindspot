0003 — How Stage 3 Actually Runs

No "why" pitch. This is the exact control flow of src/blindspot/filtering.py:53 — every branch, every string it touches, traced on your 3 fixtures. 7 minutes.

0. What it receives — the Candidate contract

discovery.py:20 Candidate{ service_a, service_b, resource, resource_type, value, evidence }
resource = bare key/name (DB_HOST, shared-data)
value = shared value if equal else None (discovery.py:67). Volumes always None (discovery.py:124).
evidence = human string discovery built — filtering reads it to detect "different values". 
Discovery already sorted by (service_a, service_b, resource_type, resource) — filtering preserves that order.

1. Constants and helper

// filtering.py:23  GENERIC_ENV_KEYS = {
  PORT, HOST, HOSTNAME, DEBUG, LOG_LEVEL, LOGLEVEL, ...,
  APP_ENV, PYTHON_ENV, RAILS_ENV, TZ, LANG,
  DATA_PATH, SHARED_EXTRA, SHARED_NOISE, ...  // conservative, never includes DB_HOST/DB_NAME
}
// filtering.py:49
def _is_generic_key(key: str) -> bool:
    return key.upper() in GENERIC_ENV_KEYS   // case-insensitive

Change this set → change what gets dropped. That's the only tuning surface.

2. The decision function — the whole heuristic

// filtering.py:86
def _decide(cand) -> (keep: bool, reason: str):
    ① if cand.resource_type == "named_volume":
          return True, "shared named volume — likely coupling"   // ★ Branch A

    ② if cand.resource_type == "env_var":
          ②a if cand.value is None and "different values" in cand.evidence:
                 return False, "same key 'X' with different values — likely coincidence (e.g. PORT)"
          ②b if _is_generic_key(cand.resource):
                 return False, "generic key 'X' — standard port/debug/logging/generic noise"
          ②c if cand.value is not None:
                 return True, "shared X='val' — specific config, likely coupling"
          ②d else:  // value is None but NOT "different values" → both None (rare)
                 return True, "shared key 'X' with no value — possible coupling, needs LLM"

    ③ // unknown type
       return True, "unknown resource_type — kept conservatively"

Order matters: ②a runs before ②b — a PORT mismatch is dropped as "different values" even though PORT is also generic. ②c requires value is not None — same key + same string.

3. The loop that builds output

// filtering.py:53
def filter_candidates(candidates):
    kept = []
    for cand in candidates:               // iterates in discovery order
        keep, reason = _decide(cand)      // deterministic, no I/O
        if keep:
            enriched = f"{cand.evidence} | filter: kept — {reason}"
            kept.append(replace(cand, evidence=enriched))  // frozen dataclass copy
        # else: dropped — not returned
    kept.sort(key=lambda c: (service_a, service_b, resource_type, resource))
    return kept

// filtering.py:76 — same logic but returns ALL annotated for testing/reporting
def filter_with_reasons(candidates) -> List[(Candidate, bool, reason)]

No mutation, no LLM call, pure function. replace keeps original Candidate immutable.

5. Edge cases the code explicitly handles

  • port vs PORT — same drop due to .upper() in _is_generic_key:50.
  • Both services define FOO with no value → discovery.py:74 gives value=None but evidence without "different values" → hits ②d → KEPT weak (needs LLM judgement).
  • Bind/anonymous volumes — never reach filtering: discovery.py:101 filters type != "named" before creating Candidates (so `tests/test_filtering.py:105` passes).
  • Unknown resource_type → branch ③ KEEP conservatively — never silently drop future types.
  • Three services with same key → discovery.py:54 combinations produces 3 Candidates; filtering runs per-pair independently.

6. Why evidence enrichment matters for what comes next

Stage 4 Judge receives enriched evidence — the " | filter: kept — ..." suffix is the provenance LLM sees. And cache.json key is hash(candidate + evidence) (AGENTS.md:85), so two identical DB_HOST=shared-db in different service contexts are not deduplicated.
